model-summary.json.

ModelImporter.java, TinySdImageGenerationAdapter.java, TinySdRunner.java,

GeneratedAdapterRegistry.java, download_model.py, and
app/generated-runtime-dependencies.gradle.kts. Preserve their contracts when

Create a model-specific class that implements ImageGenerationAdapter. Register
the adapter and exactly one active ModelDescriptor in
GeneratedAdapterRegistry.java. Add runtime dependencies only to
app/generated-runtime-dependencies.gradle.kts. Keep generated Java classes in
the org.arm.learningpath.tinysdstudio package so they can use the application
adapter contract.

The current application activates one model descriptor. A model returned by
GeneratedAdapterRegistry.models() replaces the built-in descriptor at startup.
Do not add a model selector unless the requested workflow explicitly requires
multiple models to be available in the same APK.

First compare the package with the supplied TinySD ExecuTorch contract.
Generate another adapter only when the package does not fit it. Determine the
actual task, package assets, prompt processing, callable methods, tensors,
denoising algorithm, output decoding, and required controls from the downloaded
package. Stop and report missing information rather than guessing.

Treat runtime compatibility as more than matching the model-file extension.
Inspect the package documentation and configuration for required Android
libraries, native shared objects, custom operators, delegated backends,
packaged runners, and supported application binary interfaces. Use the
package's documented Android execution path when one is provided. Do not assume
that a generic runtime API can execute the packaged model.

For ExecuTorch packages, determine whether each .pte program needs custom or
backend-specific operators that are not registered by the standard Android
runtime dependency. If the package requires a custom runner or operator
library, do not generate an adapter unless its arm64-v8a Android artifact can be
identified from trusted documentation.

If the package documents a standard ExecuTorch or XNNPACK workflow but does not
record the exact export version, the existing executorch-android dependency can
be used as a compatibility candidate. Generate the adapter, but state that
model loading remains unverified until the program runs on the target device.
Treat a load or operator-registration failure as a compatibility failure; do
not hide it with another model, runtime, or fallback path.

The generated adapter must:

- validate the selected package and every required model or configuration file
- treat ModelDescriptor.runtimeName as UI text, not a compatibility identifier
- load imported model files only from Android application storage
- implement the documented tokenizer, text conditioning, latent initialization,

- validate runtime methods, tensor shapes, and output types before inference
- keep runtime-specific code out of MainActivity.java
- report useful progress and measured generation time without invented claims
- avoid network access, credentials, absolute paths, placeholder values, and
  fallback models
- close model sessions and other native resources

Update download_model.py and ModelImporter.java only as needed to create and
import the documented package. Use an uncompressed ZIP when large model files
need random access or direct copying. Validate archive paths, sizes, and checksums
before replacing an installed package.

The shared ImageGenerationAdapter interface accepts one prompt and one seed and
returns one complete Bitmap. Stop and report that the application contracts need
to be extended when the workflow requires an input image, negative prompt,
adjustable generation controls, streaming previews, multiple generated images,
safety metadata, or another result type. Do not force the package into the
supplied interface.

Do not describe the generated adapter as supported until it has been built,
installed, and tested with representative prompts and recorded seeds on an
Arm64 Android phone or emulator.

Return complete source, registry, resource, package-handling, and dependency
